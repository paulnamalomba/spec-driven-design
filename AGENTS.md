## Skill source ownership

This repository owns the `spec-driven-design` skills. Edit each skill's source here; installed skill directories may be symbolic links to these sources. Preserve unrelated skills, repository profiles, and existing invocation/permission rules.

Before changing a skill, read its `SKILL.md` and applicable references. Preserve valid YAML metadata and validate changed skills with the available skill validator. Documentation checks do not authorize application builds, commits, or publication.

## Commit-note version profiles

`create-commit-notes` supports the convention to create commit notes for repository tags/releases. Resolve the target repository's local `AGENTS.md` and version metadata first; do not apply one project's version scheme to another.

New commit/release notes use UTF-8 Markdown (`.md`) with headings, tables and evidence links. Preserve historical `.txt` records and link them from the sole active Markdown continuation. Before migrating an automated consumer, make its readers Markdown-first with legacy text compatibility and its appenders write Markdown. This changes note presentation, not raw logs, licenses, version arithmetic or publication permissions.

The frontend has its own [profile](create-commit-notes/references/frontend-versioning.md): three single-digit version fields and a 0–99 build field (user, 17 November 2026), normal carries, and a prospective immutable `v<breaking>.<major>.<minor>` tag/release for the first accepted build of each new family. This release rule is frontend-only; preserve PETSc, SESKA and MS-MPI policies. Frontend GitHub CI remains paused by the user's direction until explicitly resumed.

SESKA/seskafeabackend also has its own profile: SESKA_INTERNAL_VERSION starts at the user's historical 1.0.0.17, with no invented historical build evidence. It uses the same bounded four-part arithmetic and three-part note grouping, but an independent counter. Read create-commit-notes/references/seska-versioning.md. Invoke notes at initialization and every minor/major/breaking transition, and preserve every accepted build progression. The release script never changes versions; successful build acceptance does.

For `petsc-native-windows`, the internal version format is `<breaking>.<major>.<minor>.<build-number>`, starting with the unbuilt seed `3.27.0.0`. Successful artifact-producing builds and required profile checks advance once; failed, skipped, configure-only, documentation-only, and no-op runs do not. Build ranges 0–99, minor 0–9, major 0–99; carry resets following fields to zero. Examples: `3.27.0.99 -> 3.27.1.0`, `3.27.9.99 -> 3.28.0.0`, `3.99.9.99 -> 4.0.0.0`. Only the initial seed is unbuilt by definition; later zero builds require normal success evidence. Invoke `create-commit-notes` at seed initialization and every minor/major/breaking change. Upstream PETSc macros and ABI identity remain separate.

PETSc note filenames omit the fourth field: `.commits/<breaking>.<major>.<minor>.md`. Every such note preserves chronological full-version/build-counter transitions, source and upstream identities, selected build profile, toolchain/dependency pins, exact commands and actual verification, artifacts/evidence, and remaining limitations. Never manufacture successful builds or advance a counter merely to write notes. See [the PETSc profile](create-commit-notes/references/petsc-versioning.md).

If this skill repository later produces a versioned distributable, establish its own version source and increase its build number only after a successful artifact-producing build and required checks. Ordinary skill prose validation does not create an application build or advance PETSc's version.

## Agent workflow

These rules apply to the orchestrator and its subagents. The suite `AGENTS.md` holds the same common rules, and every owned repository repeats them. The default branch of this repository is `main`. Here a build is the validation of the changed skills with the available skill validator, and the focused tests are the checks of the changed skills and scripts.

- **Required (user, 16 November 2026), main stays current:** once a pull request merges, its work must be on the default branch. When a PR merges into an intermediate or stacked branch, a merge agent carries that branch into the default branch at once: it merges with `--no-ff`, resolves conflicts by intent, verifies, pushes, and merges the merge PR under the user's standing authorisation for this step. Agents never merge a PR the user has not merged. Open stacked PRs against the default branch where possible, because `Closes #n` links and closes issues only for PRs into the default branch.
- **Required (user, 16 November 2026), subagent models:** subagents run Claude Opus at high effort (implementation, merges, code reviews) or Claude Fable at medium effort (lean reviews, research, tracker and evidence checks). The orchestrator works as chief of staff: it hands work to background subagents through context pointers (brief files, commits, issues) and improves the agent environment before feature work, with no workarounds. The 17 November council rules below replace this rule's model assignments for PR reviews and research councils.
- **Required (user, 16 November 2026), skill routing:** use `planning-and-task-breakdown` for features and new implementations (the broad points of the implementation roadmap) before issues are written, `multi-opinion` for architecture decisions and for `research`, and `issue-and-pr-based-development` for the tracker, branch and PR flow.
- **Required (user, 17 November 2026), work per issue or PR:** each issue or PR gets an incremental build of the whole tree with no warnings, focused tests for the modules, gates and fixtures the change touches, mutation evidence that each new test catches its defect, and a council review. Then it merges. A PR runs no full suite and no build tier, and nothing is rerun after a clean merge of the default branch. This supersedes the 16 November "test scope per step" rule and the 11 November per-build tier rule, and the rebuild sentence of the merge verification reuse rule for clean merges of the default branch.
- **Required (user, 17 November 2026), build number per merged PR:** each merged PR that changes source, tests, build files, tools or dependencies gets its own build number and a build record that holds its focused evidence: the incremental build, the focused tests, the mutation evidence and the council review. A PR that changes no build-affecting file (only docs, notes or evidence) takes no build number, with the `git diff --name-only` output as evidence; documentation-only work does not advance a build number. This repository has no version source yet (see [Commit-note version profiles](#commit-note-version-profiles)), so a skill PR takes no build number until a version source exists; until then its focused evidence goes in the PR body.
- **Required (user, 17 November 2026), phase-end full run:** the validation of every skill in the repository runs once per batch, after the implementation of the phase is done, on the batch head. Their failures are fixed then. The record of that run lists the PR build numbers it covers. Every full run keeps its complete logs. This rule saves time only. It does not relax any numerical or acceptance check at the phase-end run.
- **Required (user, 17 November 2026), build trees:** a build tree is kept until its branch merges and is rebuilt incrementally.
- **Required (user, 17 November 2026), council review per PR:** every PR gets a council review before it merges, with scores out of 10 and a "Council review" table in the PR body. A normal PR is reviewed by one Claude Haiku 5.5 (xhigh) and one Gemini 3.8 Flash (High). A big or risky PR is reviewed by one Claude Haiku 5.5 (xhigh) and two Gemini 3.8 Flash (High); big or risky means a vendor or fork patch, a whole package, a storage-format change, or a solver or numerics change. This replaces the 11 and 12 November rule of one independent code review per PR. Issue acceptance criteria plus tests remain the contract, with no prose contract freezes.
- **Required (user, 17 November 2026), research council:** a research council is three Gemini 3.8 Flash (High) and one Claude Opus (high). Decision councils stay as before.
- **Required (user, 16 November 2026), merge verification reuse:** a merge that changes no build-affecting file (only verification evidence, notes or docs) reuses the verified parent's results, with the `git diff --name-only` output as evidence. Any change to source, tests, build files, tools or dependencies is rebuilt and verified.
